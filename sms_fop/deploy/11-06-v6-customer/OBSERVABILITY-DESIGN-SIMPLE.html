What we'll track to know everything is healthy

Inventory Ledger v6 — written for a walk-through, not a code review

The goal in one sentence

Every time something important happens in the system — a file arrives, an order comes in, a calculation runs, an answer goes back to SFDC — we'll write one short note to a logbook. That logbook tells us at any moment what's working, what's not, and what just happened.

1. When a file arrives 3 notes

Files come from files.com. We log every step: did we see it, did we read it, did anything go wrong?

A file was picked up
file.picked

We save the file name, where it came from, and how big it was.

Answers: did anything actually arrive today?

Without this, "no data" looks the same as "no file was delivered" — and we can't tell which.

A file was read successfully
file.parsed

How many rows it had, how many were good, how many were bad, how long it took.

Answers: did the file look the way we expected?

A file can arrive but be malformed (missing columns, broken footer). This catches it before bad data lands in the database.

A file failed
file.failed

The file name and a short reason — "missing footer", "wrong format", etc.

Answers: which files are causing trouble, and why?

If one supplier always sends a bad format, we'll see it as a pattern instead of investigating each failure separately.

2. When an order or transaction comes in 2 notes

SFDC sends us orders. FOP sends us shipment / return / receipt events. We note each one as it lands.

An order arrived
order.received

From which tenant (e.g., IFOPEUR), how big the message was, and a timestamp.

Answers: how many orders did each customer send today? At what hour?

Useful both for capacity planning ("our peak is 11am") and for customer questions ("you said 50 orders, we only got 47 — here's the gap").

A transaction arrived
txn.received

Same shape as orders — source, size, tenant, time.

Answers: is FOP sending us the shipment confirmations we expect?

If FOP goes silent, this is the early-warning signal.

3. When the stock numbers change 3 notes

The interesting math happens here — orders reserve stock, shipments reduce it, returns add it back. We log each successful update, and every failed one.

A staging row landed in the main tables
promotion.success

Which row, how long the trigger cascade took.

Answers: how fast is the system moving from "received" to "applied"?

If this slows down, customers see ATP that's behind reality. The slower it gets, the more risk of overselling.

A staging row was rejected
promotion.failed

The reason: unknown product code, missing warehouse, bad tenant, etc.

Answers: where is the data quality problem?

If SFDC starts sending orders for a SKU we don't have a catalog entry for, we see it immediately. Most of these need the upstream team to fix something on their side, so the sooner we surface it, the better.

Stock numbers actually moved
stock.changed

Which product, which warehouse, how much it moved by, and which trigger caused it.

Answers: where did this stock go? When did this product hit zero?

When a customer says "I expected 10 units, you show 7", this is the audit trail. Also lets us see stock velocity (which products move fastest) — useful for planning.

4. When SFDC asks for stock numbers (ATP) 1 note

This is the biggest blind spot we have today. SFDC calls our database to check available stock, but we don't currently log who called or how often.

SFDC asked for stock
atp.queried

Who asked, what they filtered by (specific product? whole warehouse? everything?), how many rows came back, how long it took.

Answers: who's hitting us, how hard, and is it fast enough?

SFDC quoting flow depends on this being snappy. If queries get slow, sales slows down. With this log, we can spot slow patterns — for example, "every Monday at 9am, someone runs a query without filters and it takes 5 seconds" — and fix the root cause instead of guessing.

5. When something raises an alert 1 note

Some events deserve a notification — back-dated stock counts, validation errors, things the system shouldn't quietly swallow.

A warning or error was raised
notify.emitted

The severity (warning vs error), what triggered it, and a short message.

Answers: is anything in the system unhappy right now?

Single feed an on-call person can watch — instead of grep-ing through application logs.

6. Is the system itself still alive? 1 note

The simplest signal — a "ping" from the running service once a minute.

The service checked in
daemon.heartbeat

Just a timestamp and a "still here".

Answers: is the program even running?

If the heartbeat stops, the service crashed. Everything else going to zero looks the same as "quiet day" — but missing heartbeats are unambiguous.

The "are we okay?" check

The service exposes a simple URL — /actuator/health — that anyone (or Kubernetes) can call to ask "are you healthy right now?"

200 OK = service is running and can talk to the database. Kubernetes leaves the pod alone.

503 NOT OK = something is wrong (database unreachable, scheduler thread died). Kubernetes automatically restarts the pod.

Think of it as the "check engine" light — but instead of a vague warning, it tells you exactly which component is failing.

What we can actually see with all this

Sample questions a stakeholder can answer in 30 seconds:

How many files came in this morning, and how many had errors?

Count of file.picked vs file.failed for today, grouped by hour.

Is SFDC's stock-lookup feeling slow right now?

Average time of recent atp.queried events — chart it over time.

Has any tenant gone quiet today?

List of tenants with zero events in the last hour — usually means broken credentials or paused integration.

What product caused the most rejections this week?

Group promotion.failed events by error reason and product code.

When did this specific order get reserved?

Find the order.received event, then the matching stock.changed events — full audit trail.

Was the system down at any point last night?

Look for gaps in daemon.heartbeat — they tell you exactly when, and how long.

In one paragraph for sign-off. We're proposing to log 9 types of events (above), every event in one table, every event tagged with a tenant, a timestamp, and a tracking ID so we can follow one file all the way through. A separate URL lets Kubernetes and humans check "are you healthy?" at any moment. No new servers, no new services — just a small addition to the database the application already writes to, plus one tiny HTTP endpoint. The Grafana team can plug their dashboard straight into the same table.
